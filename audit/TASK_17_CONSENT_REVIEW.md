## Historical candidate and evidence boundaries

A first-party shared consent component is referenced once by the homepage and 50 tool pages. Its default is no Google tag or Google requests; rejection persists when localStorage is available. Acceptance loads the existing tag, explicitly keeps advertising-related consent denied, disables Google signals/ad personalization, configures automatic page views off, and queues one explicit page view per eligible page. Tool inputs and URL query strings/fragments are not intentionally included. Visitors can reopen privacy settings and withdraw; the component sets Google's disable flag immediately and removes first-party GA cookies where accessible. Pending requests already initiated during valid consent cannot be recalled. If storage is unavailable, choices are page-local and the interface explains this. A notice at `/privacy.html` describes these behaviors and third-party hosting/CDN requests.

Prior release/publication evidence remains unchanged and truthfully refers to the previously deployed tool source. `audit/TASK_17_CANDIDATE.json` binds the local candidate pages, shared component and notice to their hashes. The tracking validator accepts only the exact reversible consent loader insertion and specific privacy wording updates; it reconstructs and hashes the prior published page for each tool. Any other page change, altered prior evidence, unpassed candidate record or unbound asset remains an error. At this pre-deployment checkpoint the candidate was not publicly verified; the later deployment verification is recorded above without altering the original per-tool publication records.

## Historical validation and continuing limitations

Local Chromium tests intercept Google endpoints, covering first visit, reject, accept, revisits, direct tool navigation, one queued page view per navigation, withdrawal, changes while a tag is loading, cross-tab rejection, expiry, inaccessible storage and keyboard controls. A separate local check ran the actual Google tag with every external request intercepted and observed one page_view attempt after acceptance and none after withdrawal in the tested scenario; no measurement was sent to Google. Interception cannot prove Analytics property receipt or all future third-party behavior. The consent status is announced with native controls and ARIA, but no physical screen reader or device was tested. Subsequent live-browser checks are recorded above; the GA4 property has not been independently verified.

The site owner must review the actual controller/contact information, privacy notice, GA4 retention and enhanced-measurement/property settings, Google contractual terms and international transfer arrangements, and whether 180 days is appropriate. No legal compliance certification is claimed. [ICO consent guidance](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/how-do-we-manage-consent-in-practice/) and [Google basic consent mode](https://developers.google.com/tag-platform/security/concepts/consent-mode) are relevant.

For a reproducible local check with an actual Google tag, obtain the current public `gtag.js` for the configured measurement ID into a temporary file, set `EDB_GTAG` to that file and `EDB_TEST_BROWSER` to the local Chromium executable, then run `node --test scripts/consent-real-tag-check.mjs`. The helper intercepts all external browser requests, serves the supplied tag locally and does not send measurement events to Google. The tag itself is intentionally not bundled or committed. This optional check depends on the supplied third-party script version and is separate from the deterministic mocked CI suite.
